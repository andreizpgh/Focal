# First-pass acoustic alternatives

## What was recorded

The pinned Parakeet Ultra INT8 TDT joiner produces 8,193 vocabulary scores and five duration scores at each decision. Greedy decoding takes the winning token and advances its predictor with that token. Focal's sherpa-onnx 2.0.1 C API returns the emitted sequence, its timing and the chosen log probabilities. Its result has no field for competing tokens. The NeMo modified beam decoder also exports a single best hypothesis. [Pinned C API](../../../app/src/main/cpp/third_party/sherpa-onnx/c-api/c-api.h) · [Greedy decoder source](https://github.com/k2-fsa/sherpa-onnx/blob/af2d8d81dbfa61c4cea4c568da78f3982edca005/sherpa-onnx/csrc/offline-transducer-greedy-search-nemo-decoder.cc) · [Modified beam decoder source](https://github.com/k2-fsa/sherpa-onnx/blob/af2d8d81dbfa61c4cea4c568da78f3982edca005/sherpa-onnx/csrc/offline-transducer-modified-beam-search-nemo-decoder.cc)

There are two measurement paths. For quality, a test executable linked to the original host library observes its ONNX Runtime 1.28.2 Run outputs through the public C function table. It reads each completed joiner output and records the runner-up and third-place vocabulary IDs and their score differences from the winner. It never writes a tensor. We verify the winner for every emitted token and add the observed logit differences to its published log probability. For timing, a local build of the pinned source records the same two runners-up directly from existing log probabilities, and only for emitted tokens below 0.50 confidence. This avoids the diagnostic executable's full transcript of decisions. Neither path adds an encoder pass, changes the predictor state, or requires new weights. The upstream source archive had SHA-256 `afcafe3c34bc2f15a363ad791fa1644a69bf0977a58c1b4f617468976c2faeb5`. The host ORT shared library in both paths had SHA-256 `4b3607aebd1784b26b6f9b20e4bd974c7ab8287043e4d095cb7d2cb40b5e566e`.

This tests a single competing token on the original greedy trajectory. The remainder of a multi-piece word still follows the original prediction history. It does not explore fresh continuations after that substitution.

## What counted as an option

- Use the same 232 multilingual notes and underlines as in the wider-context experiment. Include the three separate fluent Russian checks and the repeated classroom session. Reuse the previously mapped printed-key ranges for the latter. The published holdout split has already served earlier experiments. [Corpus and sources](../2026-11-19-multilingual/method.md) · [Wider-context selection and dictation references](../2026-11-20-context-review/method.md)
- Read the original decoder window that owns each selected word, including short notes where no wider crop was available. Skip a selection with ambiguous ownership or a window whose tokens, timestamps or doubt classification differ from the archived baseline. Require log probabilities to agree to within 0.0001 for the whole window. Check a long holdout window for a language without a naturally selectable timed span. Such controls add zero suggestions to the quality count.
- Consider one substitution at a time, with at most two competitors per uncertain token. Both pieces must be letters or combining marks, keep their original word-start status, and differ beyond case. Rebuild the entire window with Focal's Kotlin WordBuilder. Accept a variant only when it changes one lexical word, leaves word boundaries and times intact, and maps exactly to an original selected word. Keep every surrounding character and the other words of a grouped selection. Never propose a new number or a change to punctuation alone.
- The **broad rule** requires candidate probability of at least 0.10 and a candidate-to-winner probability ratio of at least 0.35. Rank alternatives by that ratio, then probability, deduplicate normalized spellings, and keep at most two per tap. The **strict rule** requires 0.20 and 0.60 respectively. The original piece must cover the whole lexical word, or the candidate word must also occur at an unflagged position within 48 words of the target. Keep the best qualifying alternative. These rules were fixed before scoring. After inspecting preliminary development counts, a separate diagnostic scored all broad-rule candidates before the two-option cap. It gives the maximum number of taps this candidate pool could help if someone always picked a useful word.
- Score each option as one reversible replacement from the original draft. Compare whole-note normalized word edit distance to the published reference. A lower distance counts as helpful, even if the word was only partially repaired. Also score the existing menu in display order, and count strict options absent from it. The repeated dictation uses the local printed phrase instead of whole-note distance. Unscored words remain in the tap denominator. This measures lexical errors, independent of human review time.

## Resource comparison

Use two CPU threads, greedy decoding and the app's lower-memory setting. Benchmark eight fixed original windows with one separate warm-up per process. Run four fresh processes in off, on, on, off order and compare paired crop times from PCM read to native result. Collect peak process RSS and verify that the four runs have identical token, time and confidence receipts. The Android 35 x86-64 emulator uses two virtual cores and the app's packaged ONNX Runtime. It also runs the packaged sherpa library once as a control. The timed collector includes writing the sparse trace. Constructing menus in Kotlin/Python, database storage and user interaction are outside the timer. The guest reported 2.42 GiB RAM. During the separate packaged control, the host emulator reached its soft memory ceiling. That ceiling was raised within the original hard cap before the timed off/on rounds. Host memory pressure accounted for less than 0.01 seconds across the timed rounds sampled by the monitor. The control load is excluded from the timing comparison. These are desktop and emulator measurements.

## Reproduction

Use Python 3.11+, JDK 17, the core JAR and the original private window receipts described in the earlier study. The window request table contains a note/window ID, PCM16LE path, start and end in milliseconds. Use the pinned models and matching CPU libraries. All generated raw artifacts belong in a local build directory. [Original note receipts](../2026-11-19-multilingual/method.md) · [Window decoder and Kotlin word builder](../2026-11-20-context-review/method.md)

1. Run `scripts/first-pass-review/prepare.py WORK --input MANIFEST PLAN`, repeating the input pair for the Russian checks. Each input plan is produced by the earlier context-review planner. The new planner uses its flagged offsets and reselects the original windows.
2. Build the quality executable from `scripts/context-review/decode.cpp` and `scripts/first-pass-review/stock-observer.cpp` with C++17, the pinned C API and ORT 1.28.2 headers. On Linux link the original sherpa C library, `-ldl` and `-Wl,--export-dynamic-symbol=OrtGetApiBase`. Set `FOCAL_REVIEW_LOGITS=WORK/logits.tsv` and run it on the original windows using the invocation in the wider-context study.
3. Run `observed_ranks.py WORK models/parakeet-ultra/tokens.txt`, then `variants.py` with the same arguments. Run the existing `CropWords` with input `WORK/variants.tsv` and output `WORK/words.tsv`. Run `evaluate.py WORK PREVIOUS_RESULTS_JSON`. The latter is the previous wider-context report's results file containing the separate dictation mapping.
4. For performance, extract sherpa revision `af2d8d81dbfa61c4cea4c568da78f3982edca005`, apply `scripts/first-pass-review/collect.patch` with `patch -p1`, and copy `collect.h` next to the patched decoder source. Build the sherpa C API shared target with the pinned ORT distribution. Use that same library in all four timed processes and set `FOCAL_REVIEW_TRACE` to a writable trace path only for the on runs. The benchmark's file collector assumes one recognition stream. It is outside the Android app and its public API.
